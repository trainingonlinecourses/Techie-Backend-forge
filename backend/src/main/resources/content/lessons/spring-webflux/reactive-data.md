# Reactive Data Access — R2DBC

## The problem: JDBC is blocking

JDBC drivers block the thread while a query runs — that's the whole reason WebFlux can't use JPA/Hibernate in a request thread. The ecosystem answer: **R2DBC** (Reactive Relational Database Connectivity), a reactive SQL driver API, plus reactive repositories.

| | JDBC + Spring Data JPA | R2DBC + Spring Data R2DBC |
|---|---|---|
| I/O | Blocking | Non-blocking |
| Repositories | `JpaRepository` | `ReactiveCrudRepository` |
| Return types | `List<T>`, `Optional<T>` | `Flux<T>`, `Mono<T>` |
| ORM | Hibernate (entities, caching) | **Not an ORM** — you map rows yourself |
| Transactions | `@Transactional` (thread-bound) | `TransactionalOperator` |

Key mental shift: **R2DBC is a driver, not an ORM**. No lazy loading, no first-level cache — you write the SQL (or derived queries), get reactive streams back.

## Reactive repository

```java
public interface CustomerRepository extends ReactiveCrudRepository<Customer, Long> {

    Flux<Customer> findByLastName(String lastName);          // derived query → Flux
    Mono<Customer> findByEmail(String email);                // single → Mono
}
```

```java
@Service
public class CustomerService {

    private final CustomerRepository repo;

    public Flux<Customer> all() { return repo.findAll(); }     // streaming, row by row

    public Mono<Customer> byId(Long id) {
        return repo.findById(id)
                .switchIfEmpty(Mono.error(new CustomerNotFound(id)));
    }

    public Mono<Customer> create(Customer c) { return repo.save(c); }
}
```

Each repository method returns `Mono`/`Flux` and never blocks: the connection is released back to the pool while the DB works.

## Reactive MongoDB — the natural fit

Mongo's document model maps perfectly onto reactive streams, and `spring-boot-starter-data-mongodb-reactive` is one of the most-used reactive stacks:

```java
public interface OrderRepository extends ReactiveMongoRepository<Order, String> {
    Flux<Order> findByCustomerId(String customerId);
}
```

Same repository style, zero SQL. Reactive Mongo is often the pragmatic first reactive database for teams migrating servlet→WebFlux.

## Transactions — no @Transactional

`@Transactional` binds a connection to the *calling thread* — that doesn't exist in reactive. Use **`TransactionalOperator`**:

```java
@Service
public class AccountService {

    private final AccountRepository accounts;
    private final TransactionalOperator tx;

    public Mono<Void> transfer(String from, String to, BigDecimal amount) {
        Mono<TransferResult> work = accounts.findById(from)
                .flatMap(a -> accounts.debit(a, amount))
                .zipWith(accounts.findById(to).flatMap(a -> accounts.credit(a, amount)))
                .then();
        return tx.transactional(work);   // commit/rollback around the whole reactive chain
    }
}
```

`TransactionalOperator.transactional(publisher)` wraps the stream: commit on complete, rollback on error. You lose the magic of `@Transactional` — explicit is the price of non-blocking.

## Schema setup

```yaml
spring:
  r2dbc:
    url: r2dbc:h2:mem:///customers;DB_CLOSE_DELAY=-1
    username: sa
    password: ""
  sql:
    init:
      mode: always          # run schema.sql against the R2DBC connection factory
```

```sql
CREATE TABLE IF NOT EXISTS customers (
    id   BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(100) NOT NULL
);
```

> **Why it matters (organizational view)** — R2DBC is a real operational decision: no ORM conveniences, no lazy loading, explicit transactions. The org should adopt it for **the reactive services only**, and keep the "entity mapping" burden low by standardizing on derived queries + small row types. Also: monitor connection pool usage like you would JDBC — a reactive pool exhaustion shows up as timeouts, not thread dumps. If a service's data layer is complex relational modeling, that's a signal it belongs on servlet+JPA, not forced into reactive.

## Key takeaways

- JDBC blocks — R2DBC is the reactive SQL driver; Spring Data R2DBC gives `ReactiveCrudRepository`.
- R2DBC is a driver, not an ORM: no lazy loading/caching; you map rows yourself.
- Reactive Mongo (`ReactiveMongoRepository`) is the smoothest reactive data path.
- Transactions: `TransactionalOperator`, not `@Transactional` — explicit and non-blocking.
- Schema init via `spring.sql.init.mode: always` + `schema.sql`.
