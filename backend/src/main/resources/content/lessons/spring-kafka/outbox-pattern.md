# The Transactional Outbox Pattern

## The dual-write problem

You create an order (DB insert) **and** publish `OrderCreated` (Kafka). Two writes, two systems — they can't be atomic:

1. Save order, Kafka send fails → **event never published**, downstream never knows.
2. Publish first, DB commit fails → **phantom event** for an order that doesn't exist.

Any order of writes leaks. The classic fix: **write both to the same database, atomically.**

## The pattern

```
┌─────────────────────────── same DB transaction ───────────────────────────┐
│ 1. INSERT INTO orders (...)                                               │
│ 2. INSERT INTO outbox (event_id, topic, payload)                          │
└───────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
              Outbox relay (poller) ── reads unpublished rows
                                    │  publishes to Kafka
                                    ▼
                              topic "orders"
```

1. **Business state + outbox row commit together** — if the order insert succeeds, the outbox row is guaranteed there.
2. A **relay** (polling job or CDC like Debezium) reads outbox rows, publishes them to Kafka, and marks them published.
3. The relay only ever needs to publish **exactly once-ish**: consumers are idempotent anyway (at-least-once is the baseline).

```sql
-- outbox table
CREATE TABLE outbox (
  id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  event_id    VARCHAR(64)  NOT NULL UNIQUE,   -- idempotency for the relay itself
  topic       VARCHAR(128) NOT NULL,
  payload     JSON         NOT NULL,           -- serialized event
  created_at  TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  published   BOOLEAN      NOT NULL DEFAULT FALSE
);
```

## Writing the outbox row (Spring, same transaction)

```java
@Service
public class OrderService {

    private final OrderRepository orders;
    private final OutboxRepository outbox;

    @Transactional
    public Order createOrder(CreateOrderRequest req) {
        Order order = orders.save(new Order(req.customerId(), req.amount()));
        // Same DB transaction — atomic with the order insert:
        outbox.save(new OutboxEntry(
                "orders",
                serialize(new OrderCreated(order.getId(), order.getCustomerId(), order.getAmount()))));
        return order;
    }
}
```

That's the whole trick: **one `@Transactional` method, two inserts, one commit.** No Kafka call in the business path — the DB is the source of truth for "what happened".

## The relay (polling version — what the demo project runs)

```java
@Component
public class OutboxRelay {

    private final OutboxRepository outbox;
    private final KafkaTemplate<String, Object> kafka;
    private final ObjectMapper mapper;

    @Scheduled(fixedDelay = 2000) // poll every 2s; tune by volume/latency needs
    public void publishPending() {
        List<OutboxEntry> pending = outbox.findTop50ByPublishedFalseOrderByIdAsc();
        for (OutboxEntry entry : pending) {
            try {
                Object event = mapper.readValue(entry.getPayload(), Object.class);
                kafka.send(entry.getTopic(), event).get(5, TimeUnit.SECONDS);
                entry.setPublished(true);   // mark AFTER a successful send
            } catch (Exception e) {
                log.warn("Outbox publish failed for event {}, will retry next poll", entry.getEventId(), e);
            }
        }
        outbox.saveAll(pending);
    }
}
```

- **Order by id** keeps events in insertion order (per aggregate, use a key in the payload for per-key Kafka ordering).
- **Published flag after successful send** — a crash mid-loop re-sends the row next poll; consumers must be idempotent (they are, by rule).
- Batch limits (`LIMIT 50`) prevent one big backlog from blocking the whole relay.

## Alternatives and refinements

| Approach | How it publishes | Trade-off |
|---|---|---|
| **Polling relay** (above) | `@Scheduled` job reads outbox | Simple, up to ~1–2s latency, needs a scheduler |
| **Transactional outbox + Debezium** | CDC reads the DB binlog, publishes | Low latency, no app code, but another infra component |
| **Kafka transactions** | Producer sends in the same tx as the DB commit (chained tx manager) | Latency and complexity; still needs idempotent consumers |

Production hardening: delete or archive outbox rows after publish (retention), alert on **outbox backlog age** (a stuck relay is a silent outage), and make the relay a **single instance** (a `@Scheduled` lock, or run it on one node) or use the unique `event_id` to tolerate races.

> **Why it matters (organizational view)** — The outbox is the *consistency backbone* of an event-driven org: it's the pattern that makes "DB commit and event publish" atomic without distributed transactions. Standardize on it for every "write state AND notify the world" flow (orders, payments, user lifecycle), and treat **outbox backlog as a page-worthy alert** — rows piling up means downstream systems are silently missing events. The pattern also gives you a free audit log: the outbox table IS the ordered list of everything your service published.

## Key takeaways

- Dual-write (DB + Kafka) is never atomic — the outbox makes both writes one DB transaction.
- Business insert + outbox insert in the same `@Transactional`; the relay publishes later.
- Relay: poll unpublished rows in id order → send → mark published; crash ⇒ re-send ⇒ idempotent consumers.
- Alternatives: Debezium/CDC (low latency), Kafka transactions (complex); polling relay is the simplest correct default.
- Alert on outbox backlog; keep the relay single-instance or race-safe via unique event ids.
